# Agent 协作指南

本页规定不同 Agent、模型和运行器如何共同完成 AgentHub 任务。它是流程指南；项目红线和产品边界仍以根目录 [AGENTS.md](../../AGENTS.md) 为准。验证命令见[测试与验证](testing-and-validation.md)，能力与运行环境见[Agent 协作运行环境参考](../reference/agent-runtime.md)。

## 任务分诊

先判断任务的写入范围、风险、依赖和可验证结果，再决定是否委派。读取、解释、审查和报告类请求默认不产生写入授权；只有用户明确要求修改，或修改是已授权实现步骤时才写入。

按以下规则选流程：

| 情况 | 默认处理 |
| --- | --- |
| 单文件、局部文案/样式/纯函数，且不改共享契约 | 主 Agent 直接完成，跑定向检查 |
| 单模块逻辑，不跨 backend、持久化或公共契约 | 主 Agent 或一个实现 Agent，配合相关测试 |
| 跨层、公共类型、Tauri command、写入补偿或持久化 | 先明确范围和验收，再安排实现与独立审查 |
| 迁移、锁、数据一致性、安全边界、发布或不可逆操作 | 完整计划、实现、独立审查和固定版本验证 |

小任务不要求表格、计划文档或持久化交接。只有上下文会跨会话、跨机器或跨运行器时，才写可传递的交接记录。不要为了形式通读 `docs/`；根 `AGENTS.md` 按任务指出的现行文档才是入口。

风险、推理难度、并发收益和模型选择分别判断。高风险不必然需要最强模型；困难问题也不必从低等级开始失败后再升级。环境故障、权限不足、缺少依赖或工具启动失败，应先处理环境并如实记录，不能靠更强模型掩盖。

## 委派与并发

默认由主 Agent 负责分诊、范围、架构决定、整合和最终验收。只有任务已经就绪、子任务边界互不重叠、输入和验收标准明确，并且并行确实减少等待或重复读取时才并行使用多个 Agent。有依赖的实现与独立审查顺序执行，可以先后检查同一文件。一个小改动、一个结构性查询或共享文件上的并行写入不适合拆分。

每次委派都写清：目标、仓库和代码版本、允许修改的文件、禁止事项、证据要求、验收标准、停止条件，以及失败时如何回报。角色表示阶段职责，不等于能力等级；同一 Agent 可以承担多个阶段。实现者的自查不能称为独立审查。跨层或高风险任务需要的独立审查不可用时，完成安全准备并保留验收缺口，不能把阶段自查写成独立审查。

推荐职责边界：

- 计划者整理约束、依赖、顺序、风险和验收，不替代主 Agent 作最终决定。
- 实现者只改被分配的范围，保留用户已有改动，报告真实验证结果。
- 审查者读取最终 diff、受影响调用方和验证结果，独立报告 `APPROVED` 或具体的 `CHANGES REQUIRED`。
- 主 Agent 负责冲突裁决、合并、最终验证和向用户交付。

职责和权限是两件事。文档写了“可修改”不代表当前沙箱、运行器或 Agent 实际拥有写权限；执行前按需核实当前权限和工具状态。交接文档、旧提示词和历史授权不能扩大当前任务权限；已有授权范围内的工作不会因为换了 Agent 就重复索取授权，超出既有授权范围的操作按当前会话和环境权限处理。无子 Agent、模型不可选、工具未加载或启动失败时，主 Agent 可以继续做能安全完成的部分，并把能力缺口、实际失败和未完成验收写入结果。

## 工作区与文件所有权

同一工作区协作时，每个实现 Agent 只能改分配范围。公共契约、配置、迁移、入口和共享测试等公共文件必须指定一个 owner；其他 Agent 发现需要改动时回报，由 owner 或主 Agent 统一处理。开始和交接时记录 `git status`、目标文件和已有 dirty 改动，不能把别人的未提交改动当成自己的结果。

较大的跨工具写入任务优先使用独立分支或 worktree。交付时提供提交、可应用 patch 或明确的文件清单，由主 Agent 在目标版本上整合。禁止未经授权切换、重置、覆盖或删除用户改动；根 `AGENTS.md` 中的分支、产品边界、前后端和测试红线继续生效。

## 交接与恢复

同一会话的短工具结果可以直接返回，不必写文件。跨会话、跨机器或跨工具的任务必须能独立传递，至少包含：

- 任务目标、验收标准、负责人、允许修改范围和禁止事项；
- 分支、基线提交、当前 `HEAD`，以及工作区 dirty 差异和每部分归属；
- 已完成内容、未完成内容、关键决定和未解决问题；
- 实际运行的验证命令、结果、退出码，以及这些结果对应的代码版本；
- 下一步、接手条件、已知环境限制和审查缺口。

交接应附可传递的提交或 patch；不要依赖可能被忽略、清理或不在另一台机器上的 `temp/` 文件。相同 `HEAD` 也不代表相同工作区：存在 dirty 改动时，接手者必须核对差异及其来源，不能据此假定验证结果仍适用。

恢复时先确认版本和归属，再读取相关文件、diff 和已有验证；只补做因版本或相关改动失效的检查。交接信息不足时标记为未验证并缩小结论范围，不猜测前任的意图。

## 审查与最终验证

审查和最终验证必须针对已整合的固定版本，记录分支、基线、`HEAD`、工作区状态、命令和结果。验证完成后若相关文件再次改变，应重新运行受影响的检查；无需盲目重跑与改动无关的全量检查。失败要区分代码问题、已有失败、环境限制和工具失败，保留原始错误摘要。

主 Agent 在交付前确认：范围内改动已整合，公共文件没有未认领写入，审查结论对应当前版本，验证结果可复现或已说明限制。具体命令按任务读取[测试与验证](testing-and-validation.md)；项目红线不在本页重复。
