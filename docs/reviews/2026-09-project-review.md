# AgentHub 项目深度审查

## 这次要做什么

这是一轮只找问题、不改功能的代码审查。目标是找出会导致数据丢失、登录或路由异常、程序不稳定、界面和桌面端行为不一致，以及后续维护困难的问题。结论会尽量用简单的话写清楚：问题是什么、会造成什么影响、建议先做什么。

> 工作区已有 `src-tauri/Cargo.toml` 的未提交改动。本次不检查、不修改，也不把它当成问题。

## 计划

| 阶段 | 范围 | 重点 | 状态 |
| --- | --- | --- | --- |
| 1 | 前端页面、运行时、backend 边界与 mock | 页面是否绕过边界、出错是否被吞掉、状态是否会不同步 | 已完成 |
| 2 | Core 的 service、domain、storage、platform | 写入流程、数据一致性、错误处理、迁移与资源清理 | 已完成 |
| 3 | 本机 bridge、路由、流式转发与运行时 | 并发、超时、取消、访问限制和敏感信息暴露 | 已完成 |
| 4 | Agent 对接、配置读写、登录信息刷新 | 各 Agent 的差异是否会损坏配置或产生错误路由 | 已完成 |
| 5 | Tauri、CLI、自动化与测试覆盖 | 桌面命令参数、错误返回、重要流程有没有测试保护 | 已完成 |
| 6 | 汇总与复查 | 去重、按影响排序、抽查证据；只记录能复现或有明确代码依据的问题 | 已完成 |

## 记录规则

- 只记录有明确文件和代码位置依据的问题；猜测会标为“需要确认”。
- 同一个根因只记一次，并列出受影响位置。
- 优先级：**高**=可能造成数据、登录、路由或安全问题；**中**=常见异常或明显错误体验；**低**=维护成本或边缘情况。
- 本文档会随各阶段完成逐步追加结果；没有发现问题的范围也会说明。

## 第一轮结果（代码阅读）

这一轮没有改代码，也没有跑测试。下面的问题均有对应代码位置；优先处理“高”。

### 高：可能丢数据、泄露 API Key，或让路由不安全

1. **旧的用量记录可能在升级时被删掉。** 迁移把缺少会话号和内容标记的多条历史记录当成重复项，只留一条。影响是用量和费用统计变小。位置：`crates/agenthub-core/src/storage/migrations/00021_usage_dedup_nulls.sql:5-17`。建议：缺少两个标记的旧记录不要去重，并补迁移样例测试。
2. **重新收集用量时，两个任务可能互相清空结果。** 清空记录、重置进度、标记完成分开写入；并发时可能最后显示“已完成”但记录为空。位置：`crates/agenthub-core/src/services/usage_service.rs:590-592,625-627`。建议：把这些步骤放进同一个数据库事务。
3. **同步和停用同一个 Skill 可能打架。** 两条流程同时改文件和状态，没有使用同一把锁；界面说已停用时，本机文件可能仍在。位置：`crates/agenthub-core/src/services/skill_service/sync.rs:57-59,151-153,304-359`。建议：统一锁顺序，并为并发场景补测试。
4. **Windows 上本机转发端口可能被其他程序抢占。** 监听端口时始终打开复用选项；Windows 的语义可能允许另一个本机程序同时绑定。影响是请求可能被抢走，连同本机转发的登录信息。位置：`crates/agenthub-core/src/bridge/host/lifecycle.rs:539-545`。建议：Windows 使用独占绑定，Unix 才开启复用。
5. **部分路线的上游地址没有经过安全检查。** 从路线索引取出的地址直接拼接并带着上游 API Key 请求；可被错误配置指向内网 HTTP 服务。位置：`crates/agenthub-core/src/bridge/host/transport/failover.rs:714-742`、`bridge/route_index.rs:31,97-100`。建议：所有上游地址共用同一套 HTTPS/本机地址校验，拒绝账号信息和片段。
6. **DSH 的 YAML API Key 会被错误读回。** 含引号、反斜杠或换行的值采用手写解析，转存后内容可能改变，后续切换会写坏 API Key。位置：`crates/agenthub-core/src/adapters/dsh.rs:491-522,662-672`。建议：使用 YAML 库，或完整实现转义并拒绝不支持的换行。
7. **直接应用多文件配置时可能只成功一半。** Pi、Codex、DSH 逐个写文件，后一个失败不会恢复前一个，造成登录和模型配置对不上。供应商切换已有外层恢复；问题在直接应用配置的路径。位置：`crates/agenthub-core/src/adapters/pi.rs:963-971`、`integrations/agents/codex/config.rs:440-448`、`integrations/agents/dsh/config.rs:171-185`。建议：在这些写入内加入可恢复的多文件提交。
8. **Pi 刷新登录信息接受空 token，极端过期时间还可能溢出。** 空字符串会被当作成功；不可信的过期秒数直接乘 1000。位置：`crates/agenthub-core/src/oauth/pi_refresh.rs:75-94`。建议：拒绝空 token，限制过期时间并做安全计算。
9. **桌面界面可以要求启动任意本机程序。** Tauri 命令接受前端传来的路径，只检查存在就启动。若页面被注入恶意脚本，能借桌面权限运行其他程序。位置：`src-tauri/src/commands/install.rs:339-361`、`src-tauri/src/file_manager.rs:558-608`。建议：前端只传 Agent 名称，由后端从已发现的程序中选路径。
10. **界面日志可以被写入完整 API Key。** 日志命令把前端传来的字段原样记录，和“不要记录原始敏感信息”的承诺不一致。位置：`src-tauri/src/commands/settings.rs:80-102`。建议：只允许固定字段和长度，并对所有外部文本脱敏。

### 中：会误导用户、留下资源，或增加发布风险

> 复查后，第 3、4、5 项从“高”调整到此处；原先“配置目录相对路径”一项属于有意支持的环境变量行为，已删除。

1. **路线活动加载失败会显示“没有活动”。** 查询失败被替换为空列表，页面只显示另一类错误。位置：`src/pages/routes/activity/index.tsx:150-164,413-418`。建议：单独保存查询错误并显示重试。
2. **开发环境的 Agent 列表并发加载可能被旧结果覆盖。** 同一轮的两个请求没有序号保护，一个旧失败能清空刚加载成功的列表；当前生产只有一个调用点，主要影响开发和后续维护。位置：`src/app/runtime/agent-catalog-store.ts:92-120`、`src/main.tsx:92-116,180-184`。建议：合并同时请求，或按请求序号丢弃旧结果。
3. **共享端口上强制停止路线后，慢上传仍会占用一段时间。** 已接收请求没有跟随停止信号取消读取；专用端口最终会被关闭，共享端口的场景最长接近请求体 30 秒超时。位置：`crates/agenthub-core/src/bridge/host/admission.rs:31-46`、`bridge/host/http.rs:163-188`、`bridge/host/lifecycle.rs:625-658`。建议：读取请求时也监听停止信号。
4. **OAuth 服务返回的错误文本可能进入日志。** 上游错误原样写入警告日志，也原样放进错误返回；少数服务可能回显 token。位置：`crates/agenthub-core/src/oauth/providers.rs:306-321`。建议：写日志和返回前都做脱敏。
5. **共享库导入 Skill 中途失败会留下未登记的目录。** 目录已替换，但记录文件没写成功时，没有自动恢复流程；内容通常还在，之后可用覆盖导入修复。位置：`crates/agenthub-core/src/services/skill_service/install.rs:605-644`。建议：复用已有的带恢复记录的提交流程。
6. **切换登录或供应商后，可能实际已切换却提示失败。** 切换已经提交，之后保存“撤销”信息失败，接口就报错；用户可能重复操作。位置：`crates/agenthub-core/src/services/account_service/switch_saga.rs:191-220`、`services/provider_service/switch_saga.rs:170-200`。建议：把两类写入放进同一事务，或把撤销信息的失败单独处理。
7. **本机转发的会话记录会一直增长。** 会话和续接记录没有数量或时间上限；长期运行、请求很多时可能占满内存。位置：`crates/agenthub-core/src/bridge/account.rs:237,610-625`、`bridge/host/continuation.rs:17-18,52-65`。建议：加入有上限、会过期的缓存。
8. **发布脚本测试不在 PR 检查中。** 这些脚本的问题可能要到打 tag 才发现，但发布流程会在公开发布前失败。位置：`package.json:45-48`、`.github/workflows/pr-ci.yml:75-88`、`.github/workflows/release.yml:128-131`。建议：PR 中运行 `pnpm release:test`；Windows 任务再运行版本更新脚本测试。
9. **PR 没有 Windows/macOS 的编译或测试。** 两个平台专用代码可能合入后才在发版任务发现，但不会直接发布。位置：`.github/workflows/pr-ci.yml:17,87`、`.github/workflows/release.yml:228-274,285-377`。建议：至少增加两个平台的 GUI 编译检查。
10. **release 分支的“禁止直接提交”检查发生在提交之后。** 是否真的能直接提交取决于 GitHub 上的分支保护，仓库内无法确认；若没有保护，失败检查不能让分支回退。位置：`.github/workflows/release-branch-guard.yml:3-8,51-103`。建议：检查并启用 GitHub ruleset/分支保护。

## 已确认没有明显问题的范围

- 页面没有绕过 Tauri/backend 边界；生产构建和 mock 的隔离规则总体符合架构说明。
- 本机转发主入口绑定在 `127.0.0.1`，主路线会检查 HTTPS/本机 HTTP，认证比较和请求/流大小限制已有保护。
- 单文件配置写入有临时文件和落盘处理；常见的命令启动没有通过 shell 拼字符串。
- CLI 的破坏性操作默认需要确认，输出会隐藏 API Key；发布元数据的版本一致性检查较完整。

## 建议处理顺序

1. **先保护数据和 API Key：** 用量迁移、用量重建并发、路线候选地址校验、Windows 端口独占、界面日志脱敏、桌面启动命令限制。
2. **再保证切换完整：** DSH YAML、Pi 刷新结果校验、直接应用多文件配置、Skill 同步/停用并发。
3. **最后补稳定性和发布保障：** 会话缓存上限、路线活动错误提示、停止慢上传、PR 的跨平台和发布脚本检查。

## 复查结论

第一轮发现已完成交叉复查。保留 **10 个高优先级**和 **10 个中优先级**问题；删除了 1 个证据不足的环境变量问题，并下调或收窄了 7 个问题的影响范围。下一步可以按上面的顺序修复，并为每个问题先补能复现的测试。
