# Agent 协作指南

本页规定派工、交接和审查的具体做法。风险分级、默认执行方式和最小验证表在 [AGENTS.md「协作」](../../AGENTS.md#协作)，这里不重复。

## 委派与并发

1. 派工时写全以下内容，不假设接收者知道上下文：

   ```text
   目标与验收标准：
   仓库、基线和当前改动：
   负责文件、权限与禁止事项：
   适用规则和必读章节：
   依赖、预期回传与停止条件：
   ```

2. 按角色分工：计划者定方案和依赖，实现者只改指定范围，审查者看实际 diff。角色不绑定模型。
3. 有依赖的实现和审查按顺序做；独立调查或改不同文件的实现可以并行。公共文件要改时交回负责人。
4. 要求回传结论、改动文件、验证结果和遗留问题。同一会话的小任务直接回传，不另建记录。
5. 跨工具的大型写入可用独立分支或 worktree，由主 Agent 整合。工具能力不足时查 [Agent 能力与工具：工具能力](../reference/agent-runtime.md#工具能力)。

## 交接与恢复

1. 跨会话、跨机器或跨工具时，留下这份记录：

   ```text
   目标、验收标准与负责范围：
   分支、基线、HEAD、未提交差异及归属：
   已完成、未完成与关键决定：
   验证命令、退出码、结果及对应版本：
   下一步、环境限制与审查缺口：
   ```

2. 有代码改动时附提交或 patch，不依赖对方拿不到的临时文件。
3. 接手者先核对版本和差异，再决定旧结论是否还适用。相同 HEAD 不代表未提交内容相同。
4. 交接只提供背景，不扩大当前授权，也不要求重复索取已有授权。

## 审查与验证

### 日常改动

1. 开始前记下目标分支、基线、HEAD 和未提交差异；审查从这个版本的 diff、受影响调用方和验证结果入手。
2. 审查者给出 `APPROVED`，或带文件位置、触发条件和证据的 `CHANGES REQUIRED`。顺序调用另一位审查者也算独立审查。
3. 主 Agent 整合后，按 [测试与验证](testing-and-validation.md) 跑适用检查，记下命令、退出码和所测版本。之后再改只让受影响的证据失效，补验那部分即可。
4. 交付时写明未完成的审查、未运行的检查及原因，区分代码问题、已有失败和环境限制。

结果：每次交付都能对应到一个版本、一组命令和明确的审查结论。

### 全项目体检

体检不是日常审查，默认只读。唯一可写的仓库文件是本次报告 `docs/archive/<YYYY-MM-DD>-project-review-<HEAD前8位>.md`；不覆盖已有报告，同一 HEAD 的同一次体检可继续更新同一文件。`docs/reviews/` 已迁入归档，不再作为现行目录。

1. 子 Agent 只读，不再派生；只有主 Agent 写报告。
2. 候选问题先标「待核实」，核实后改为确认、误报、已存在或范围外。正式问题要有源码、测试、运行结果或明确契约；风格偏好和项目明确不做的事不算缺陷。
3. 每条证据写明等级：源码确认、测试确认、本机复现、契约冲突、理论风险，或受环境限制未验证。
4. 报告保留确认问题、误报裁决、验证命令、未覆盖范围和残余风险，结论选 `BLOCK`、`OK WITH REQUIRED FIXES`、`OK WITH NOTES` 或 `OK`。
5. 旧报告只用来避免重复调查，每一项都要在当前 HEAD 重新验证。
