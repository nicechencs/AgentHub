# AgentHub 项目深度审查

## 这次要做什么

这是一轮代码审查，并已按核对后的改法修复大部分问题。目标是找出会导致数据丢失、登录或路由异常、程序不稳定、界面和桌面端行为不一致，以及后续维护困难的问题。结论会尽量用简单的话写清楚：问题是什么、会造成什么影响、现在修了没有。

## 计划

| 阶段 | 范围 | 重点 | 状态 |
| --- | --- | --- | --- |
| 1 | 前端页面、运行时、backend 边界与 mock | 页面是否绕过边界、出错是否被吞掉、状态是否会不同步 | 已完成 |
| 2 | Core 的 service、domain、storage、platform | 写入流程、数据一致性、错误处理、迁移与资源清理 | 已完成 |
| 3 | 本机 bridge、路由、流式转发与运行时 | 并发、超时、取消、访问限制和敏感信息暴露 | 已完成 |
| 4 | Agent 对接、配置读写、登录信息刷新 | 各 Agent 的差异是否会损坏配置或产生错误路由 | 已完成 |
| 5 | Tauri、CLI、自动化与测试覆盖 | 桌面命令参数、错误返回、重要流程有没有测试保护 | 已完成 |
| 6 | 汇总与复查 | 去重、按影响排序、抽查证据；只记录能复现或有明确代码依据的问题 | 已完成 |

## 记录规则

- 只记录有明确文件和代码位置依据的问题；猜测会标为“需要确认”。
- 同一个根因只记一次，并列出受影响位置。
- 优先级：**高**=可能造成数据、登录、路由或安全问题；**中**=常见异常或明显错误体验；**低**=维护成本或边缘情况。
- 本文档会随各阶段完成逐步追加结果；没有发现问题的范围也会说明。

## 本轮修复（2026-09-04）

按核对后的改法落地。**暂缓**：高 10（当前页面一般只传后 4 位，严重程度有异议）、中 2（生产几乎踩不到，已降为低）、中 10（要在 GitHub 开启分支保护，仓库内改不了）。

已升级并跑过旧 `00021` 的用量库，删掉的行找不回来；未跑过的升级会保留「两个标记都空」的记录。

### 高：可能丢数据、泄露 API Key，或让路由不安全

1. **旧的用量记录可能在升级时被删掉。** **已修复。** 缺少两个标记的行先打上稳定的 `orphan:<id>`，再去重。已跑过旧迁移的库无法恢复。位置：`00021_usage_dedup_nulls.sql`。
2. **重新收集用量时，两个任务可能互相清空结果。** **已修复。** 清空、重置进度、标记完成放进同一事务；整次收集加锁。
3. **同步和停用同一个 Skill 可能打架。** **已修复。** 与安装同一把根锁 + Skill 锁；卸载不再二次抢锁。
4. **Windows 上本机转发端口可能被其他程序抢占。** **已修复。** Windows 独占绑定；Unix 仍复用。
5. **部分路线的上游地址没有经过安全检查。** **已修复。** 启动规格与候选拼接共用 HTTPS / 本机 HTTP 校验。
6. **DSH 的 YAML API Key 会被错误读回。** **已修复。** 凭据文件改用 YAML 库读写。插件补丁扫描仍是手写，不是 Key 文件。
7. **直接应用多文件配置时可能只成功一半。** **已修复。** Pi / Codex / DSH 写入失败会按快照恢复。进程崩溃仍可能留下半成品。
8. **Pi 刷新登录信息接受空 token，极端过期时间还可能溢出。** **已修复。** 拒绝空 token；过期时间封顶并用饱和运算。
9. **桌面界面可以要求启动任意本机程序。** **已修复。** 只传 Agent 名称和启动类型，由本机检测结果选路径。
10. **界面日志可以被写入完整 API Key。** **暂缓。** 现有页面一般只传后 4 位；命令本身仍未强制脱敏。

### 中：会误导用户、留下资源，或增加发布风险

> 复查后，第 3、4、5 项从“高”调整到此处；原先“配置目录相对路径”一项属于有意支持的环境变量行为，已删除。

1. **路线活动加载失败会显示“没有活动”。** **已修复。** 失败单独提示并可重试；已有列表会保留。
2. **开发环境的 Agent 列表并发加载可能被旧结果覆盖。** **暂缓。** 生产只有一处加载；reset/seed 竞态已有世代号。
3. **共享端口上强制停止路线后，慢上传仍会占用一段时间。** **已修复。** 读请求体同时听停止信号。
4. **OAuth 服务返回的错误文本可能进入日志。** **已修复。** 只记状态和白名单错误码，不再回传原文。
5. **共享库导入 Skill 中途失败会留下未登记的目录。** **已修复。** 导入改走带恢复的提交。
6. **切换登录或供应商后，可能实际已切换却提示失败。** **已修复。** 「当前项」和「撤销」写进同一事务。
7. **本机转发的会话记录会一直增长。** **已修复。** 粘滞最多 4096 / 24 小时；续接最多 8192 / 2 小时。
8. **发布脚本测试不在 PR 检查中。** **已修复。** PR 跑 `pnpm release:test` 和 `release-update` 脚本测试。
9. **PR 没有 Windows/macOS 的编译或测试。** **已修复。** PR 增加 Windows / macOS 的 `cargo check`（不打包）。
10. **release 分支的“禁止直接提交”检查发生在提交之后。** **暂缓。** 需要仓库管理员在 GitHub 启用分支保护；CI 只能事后失败，不能回退提交。

## 已确认没有明显问题的范围

- 页面没有绕过 Tauri/backend 边界；生产构建和 mock 的隔离规则总体符合架构说明。
- 本机转发主入口绑定在 `127.0.0.1`，主路线会检查 HTTPS/本机 HTTP，认证比较和请求/流大小限制已有保护。
- 单文件配置写入有临时文件和落盘处理；常见的命令启动没有通过 shell 拼字符串。
- CLI 的破坏性操作默认需要确认，输出会隐藏 API Key；发布元数据的版本一致性检查较完整。

## 建议处理顺序

1. **先保护数据和 API Key：** 用量迁移、用量重建并发、路线候选地址校验、Windows 端口独占、~~界面日志脱敏~~（暂缓）、桌面启动命令限制。 **除高 10 外已做。**
2. **再保证切换完整：** DSH YAML、Pi 刷新结果校验、直接应用多文件配置、Skill 同步/停用并发。 **已做。**
3. **最后补稳定性和发布保障：** 会话缓存上限、路线活动错误提示、停止慢上传、PR 的跨平台和发布脚本检查。 **除中 2、中 10 外已做。**
