# AgentHub 全项目独立 review 提示词

本页用于发起一次只读的全项目 review。主 Agent 可按实际需要使用当前运行环境中可发现的 Agent、模型和工具，但最终结论必须由当前源码、本机验证和项目约定共同支持。

## 使用方式

将下面的提示词交给位于 AgentHub 仓库根目录的 Agent。默认审查当前工作区；如需审查指定提交、分支或 diff，应在提示词前补充目标范围。

## 提示词

```text
你是 AgentHub 本次 review 的总负责人。请对当前本机仓库执行一次证据驱动、可复现、面向实际交付的全面审查。

【目标】

从以下角度评估当前项目：

1. 架构和职责边界是否合理；
2. 是否存在真实可触发的代码 Bug、回归或异常路径遗漏；
3. 实现是否符合项目约定、现行文档和既有设计；
4. 是否存在重复规则、不必要复杂度、过度抽象或错误抽象；
5. 当前成熟度是否足以支持真实用户长期使用；
6. 对失败、并发、跨平台、数据一致性、升级兼容和资源清理是否考虑全面；
7. 测试是否验证真实行为和失败路径；
8. 文档、代码、测试和本机实际情况是否一致；
9. 最近改动是否引入新的风险。

不要以“发现问题数量”为目标。正式问题必须有源码、测试、运行结果、配置、提交历史或明确契约作为证据。

【项目规则和权限】

- 仓库：当前工作目录下的 AgentHub。
- 日常开发和合入分支是 dev；release 只用于正式发版。
- 本次默认只做 review，不修改生产代码、测试、现行架构说明或用户配置。
- 唯一默认允许写入的仓库文件是本次 review 报告。
- 不提交、不推送、不合并、不发版，不切换、重置或改写分支。
- 不删除或覆盖用户数据。
- 不显示 API Key、Token、Cookie、登录信息或其他隐私内容。
- 如需修复，只记录最小修复建议；等待用户明确授权后再修改代码。

首先完整阅读并遵守：

- AGENTS.md
- docs/architecture/overview.md
- docs/guides/testing-and-validation.md
- docs/STYLE.md 中与 review 报告有关的元数据和文档规则

按实际范围读取其他现行文档。不要为了形式通读 docs/，不要把 docs/archive/、提案或旧 review 当成当前实现。

项目明确排除的事项不得列为缺陷或待办：

- 登录信息落盘加密；
- 国产 OAuth 对接；
- 把 OAuth 转成 API；
- 按所属 Agent 禁止共享 API Key。

【固定交付路径】

开始 review 后，由主 Agent创建并维护一份最终报告：

    docs/reviews/<YYYY-MM-DD>-project-review-<HEAD前8位>.md

例如当前 HEAD 为 06b893c4、日期为 2026-09-07 时，路径必须是：

    docs/reviews/2026-09-07-project-review-06b893c4.md

规则：

1. 不覆盖 docs/reviews/2026-09-project-review.md 或其他既有审查记录；
2. 同一 HEAD 的同一次 review 可以继续更新同一报告；不同 HEAD 或新一轮 review 新建文件；
3. 只有主 Agent写最终报告。subagent 返回只读审查结果或临时输出，不并发修改该报告；
4. 报告必须使用小写 kebab-case 文件名，并包含：

    ---
    title: AgentHub 项目 review（YYYY-MM-DD，HEAD前8位）
    type: status
    status: current
    owner: maintainers
    updated: YYYY-MM-DD
    scope: 审查分支、基线与 HEAD
    ---

5. 报告是审查记录，不是现行架构契约。不要仅因发现问题就修改 docs/STATUS.md 或架构文档；实现事实发生改变时才按项目规则同步现行文档；
6. 先写入审查范围和运行信息，再逐阶段更新。候选问题必须标为“待核实”；核实后改为“确认”“误报”“已存在”或“范围外”；
7. 最终报告必须保留确认问题、误报裁决、验证命令、未覆盖范围和残余风险；
8. 写完后运行 pnpm check:docs。若检查失败，修复本报告造成的格式、元数据或链接问题；不得借机修改无关文档。

【确认审查对象和基线】

先执行并记录：

    git status --short --branch
    git rev-parse HEAD
    git branch --show-current
    git log -15 --oneline --decorate
    git diff --stat
    git diff --name-status
    git diff --cached --stat
    git diff --cached --name-status

审查开始时固定记录目标 HEAD、分支、工作区和暂存区状态，作为本轮证据基线。review 期间如果主 Agent、其他 Agent 或外部工具改变了工作区、暂存区、分支或 HEAD，只将依赖已变化状态或受影响文件的 diff、行号和验证结果标记为失效并重新采集；未受影响的只读证据可以保留，但要说明为何仍适用。报告文件自身的更新不使源码证据失效。若目标 HEAD 或比较范围改变，需为剩余审查建立新基线，不得把不同版本的观察拼成一个结论。最终报告要同时写明初始基线和最终复核状态。

不要一开始把巨大 diff 或全仓内容全部塞进上下文。先用统计和文件列表确定范围，再按需读取具体 diff。

按以下规则确定目标：

1. 工作区有改动：重点审查工作区 diff、暂存区 diff 及其影响范围；
2. 工作区干净但当前分支领先明确基线：审查基线到 HEAD 的改动；
3. 当前位于 dev 且本机 origin/dev 与 HEAD 一致：执行当前项目健康检查，优先关键边界、近期提交和高风险路径；
4. 未经授权不得 fetch、pull、checkout、reset 或 rebase；本机 origin/dev 可能陈旧，报告必须明确这一点；
5. 全项目 review 不能声称逐行穷尽。报告必须提供覆盖清单，区分深入检查、抽样检查和未检查范围。

在报告中写明：分支、HEAD、比较基线、工作区状态、本机远程引用状态、重点目录、抽样方法和未覆盖范围。

【Agent、模型和委派】

你可以按实际需要使用当前运行环境中能发现且确实可执行的 Agent、模型或其他只读工具。具体能力等级、发现方式和环境限制见仓库根目录下的 `docs/reference/agent-runtime.md`；本提示词不假定某个 provider、模型名、CLI、编排 API 或并发接口一定存在。

如果需要委派或选择模型，先读取 `docs/guides/agent-workflow.md` 和 `docs/reference/agent-runtime.md`，再按当前环境的能力发现机制行动；只做主 Agent 顺序审查时，按任务条件读取相关页面即可。

必须遵守：

1. 委派前先读取 `docs/guides/agent-workflow.md` 和 `docs/reference/agent-runtime.md`，并使用当前环境公开的能力发现机制核实可用项；记录发现来源、时间、可用能力和不可用原因。无法发现时如实写明，不得把猜测当成注册信息；
2. 使用运行时实际返回的 Agent/model/tool 标识。指定能力不可用时不得伪造结果；可以由主 Agent 顺序完成同一只读范围，但必须说明没有形成独立 Agent 或多模型证据；
3. 不为了凑数量而委派。只有目标、文件边界和证据面彼此独立时才并行；并发必须由当前环境明确支持，否则顺序执行。不得把顺序复核冒充并行独立审查；
4. 每个任务写清目标、仓库和固定基线、只读权限、重点文件或边界、证据标准、输出格式和停止条件。子 Agent 不修改项目文件、不提交、不调用新的 Agent；
5. 不给多个 Agent 完全相同的任务。按架构、正确性、测试、成熟度或反方验证划分独立证据面；主 Agent负责整合、复核和最终裁决；
6. 模型或工具意见只是证据。主 Agent必须回到固定基线对应的源码和验证结果去重、复核和裁决；工作区或 HEAD 变化后，按前述基线规则重新采集；
7. Agent、扩展、模型或外部运行器失败时，报告真实失败、运行状态和环境情况；不得静默换执行方式后声称原计划成功。

如果当前环境没有可用的委派能力，主 Agent 可以顺序完成只读审查，但报告必须明确没有独立 Agent 或多模型复核。若有另一位独立的只读审查者，顺序调用同样可以形成独立审查；记录其实际 Agent/model/tool、上下文、固定基线和证据范围，不把实现者自查称为独立审查。只有并发能力得到当前环境支持时才并行，不得把顺序复核冒充并行执行。结构索引能直接回答的问题（例如符号定义、调用方、影响范围）应由主 Agent先使用；只有索引不可用、过时或不足以回答问题时，才增加 scout 或定向读取，不把结构问题默认交给 scout。

【能力选择和证据成本】

按任务难度使用满足要求的最低成本能力；详细等级和升级条件见仓库根目录下的 `docs/reference/agent-runtime.md`。本 review 还必须遵守以下证据和成本规则：

1. 低成本能力适合证据提取、目录或符号清单、分段读取、diff 分类、测试定位、日志整理和候选问题初筛；不得单独确认 P0/P1、架构结论、安全结论或最终 verdict；
2. 强能力用于跨层架构、并发与事务、数据损坏风险、安全边界、复杂状态机、跨平台根因、相互冲突证据和最终裁决；不要让它重复机械扫描；
3. 大文件或宽范围搜索先形成有界摘要，只传递路径、符号、行范围和必要上下文；不把 node_modules、target、dist、生成文件、无关日志或整仓搜索结果发送给模型；
4. 同一文件或同一证据不得无理由被多个能力完整重复读取。子任务达到证据要求后立即停止；高风险线索只上报证据和升级理由，由总负责人决定后续复核；
5. 报告的“多模型记录”必须写明实际 Agent/model/tool 标识、能力层级（若运行时提供）、任务类型、升级原因、不可用项和是否减少了重复读取与 token 消耗。没有使用多模型时明确写“未使用”。

可按需要采用以下只读分工：

- 快速 scout：目录、符号、调用方、大文件分段和候选证据定位；
- 架构与边界：React 页面、app/runtime、backend、Tauri、Rust core 的责任和依赖方向；
- 正确性：状态机、错误路径、并发、事务、文件写入、进程、协议转换和跨平台行为；
- 测试与验证：contract、mock/生产差异、关键失败路径和测试有效性；
- 成熟度：恢复能力、日志、兼容性、维护成本、安装升级和长期运行；
- 反方审查：尝试推翻候选问题，排除风格偏好、旧问题、重复问题和范围外建议。

【重点审查面】

架构与边界：

- 页面是否绕过 backend 直接调用 Tauri；
- 是否只有 src/lib/backend/tauri/ 调用 invoke；
- mock 是否可能进入生产构建；
- 非 Tauri 生产页面是否会静默回退到 mock；
- src/lib/api/ 兼容层是否形成重复业务规则；
- Tauri shell、CLI 是否复制 core 业务规则；
- 当前实现和未来提案是否被混淆。

Bug 与正确性：

- 空值、边界值、错误分支、竞态、重复执行、取消和超时；
- SQLite 事务、迁移、幂等性和部分成功；
- 文件写入、备份、恢复、锁和资源清理；
- 登录、连接、路由、会话、Chat、stream/SSE 状态机；
- Windows、macOS、Linux 的路径、命令启动和退出差异；
- command 名、DTO、序列化和前后端字段一致性；
- 错误被吞掉、失败误报成功、数据丢失或配置损坏。

合理性与成熟度：

- 是否存在多个规则来源、过度抽象、抽象不足或分支爆炸；
- 临时兼容代码是否已经长期化；
- 错误提示是否能帮助用户继续操作；
- 安装、升级、卸载、网络失败和进程退出是否可恢复；
- 日志是否足以定位问题且不会泄露 API Key 或登录信息；
- 是否依赖隐式时间顺序、环境变量或用户目录状态；
- 文档是否把未实现能力写成当前能力。

测试：

- 测试是否覆盖真实失败路径，而不只是调用次数和成功路径；
- Vitest 是否固定使用 mock backend；
- mock 是否偏离生产 contract；
- Tauri command 名和参数形状是否被验证；
- Rust 测试实现是否放在独立测试文件；
- 测试是否会读写真实用户 home 或真实登录信息；
- 迁移、锁、补偿、状态机和协议转换是否缺少保护；
- 是否存在测试通过但生产构建失败的边界缺口。

旧 review 只用于防止重复调查。对其中每项都必须在当前 HEAD 重新验证，不得复制旧结论。已修复或当前不可达的问题标为 stale/误报，不重新列为当前缺陷。

【本机实际验证】

允许并鼓励做必要的只读调查，例如：

- Node、pnpm、Rust、Cargo、Tauri 和相关 CLI 版本；
- 当前操作系统、CPU 架构和 PATH 中真实存在的命令；
- lockfile、Cargo metadata、构建脚本和项目配置；
- 本机 Agent CLI 的实际路径、版本和启动方式；
- 文件路径、权限、端口、进程与跨平台分支；
- Git 历史中相关代码的演变。

运行测试或构建可以产生项目内标准缓存、target、dist、日志和测试产物，但不得修改真实用户配置、真实登录信息或用户数据。不要登录外部服务，不触发真实付费请求，也不要启动会改写真实 Agent 配置的流程。

区分以下证据等级：

- 源码确认；
- 测试确认；
- 本机复现；
- 契约冲突；
- 理论风险；
- 环境限制下未验证。

本机行为与推断冲突时，以可重复的实际证据为准，并解释冲突原因。

【验证策略】

根据风险选择最小、最相关的验证。可使用：

    pnpm typecheck
    pnpm typecheck:test
    pnpm test -- --run <相关测试>
    pnpm test:contracts
    cargo test -p agenthub-core --locked <filter>
    cargo test -p agenthub-cli --locked <filter>

只有审查范围确实涉及生产边界、依赖、发布或广泛改动时，才考虑：

    pnpm build
    pnpm test:pr
    cargo test --workspace --locked

记录完整命令、退出码和关键结果。失败时保留原始错误摘要，区分当前代码问题、已有失败、环境问题和偶发失败。不要通过放宽断言隐藏回归，也不要用无关的全量测试制造“验证充分”的印象。

【问题证据标准】

正式问题至少满足一项：

1. 有明确复现步骤；
2. 有具体可达的错误路径；
3. 有失败测试或验证输出；
4. 与当前代码契约直接冲突；
5. 与项目明确架构边界冲突；
6. 会导致可说明的用户影响、数据风险或平台回归。

每个候选问题先分配稳定编号，例如 AHREV-P1-001。主 Agent复核后将它分类为：

- confirmed：当前 HEAD 确认存在；
- stale：旧版本存在，但当前 HEAD 已修复或不可达；
- duplicate：与其他问题同一根因；
- invalid：被源码、测试或契约推翻；
- out-of-scope：违反项目范围或需要未授权决定；
- needs-evidence：证据不足，不能阻断。

正式报告的“确认问题”只收录 confirmed。同一根因只记录一次，并列出所有受影响位置。

严重级别：

- P0：可能造成严重数据破坏、安全事故、应用不可用或发布阻断；
- P1：真实可触发的重要 Bug、明显回归或关键契约错误；
- P2：非阻断但值得修复的正确性、维护性、测试或成熟度问题。

每个确认问题必须包含：

- 编号与严重级别；
- 简短标题；
- 文件路径和尽可能准确的行号或符号；
- 触发条件；
- 实际行为与预期行为；
- 用户或系统影响；
- 证据等级和具体证据；
- 最小修复方向；
- 推荐验证方法；
- 置信度：高、中或低。

以下内容不能列为确认问题：

- 没有可达路径的猜测；
- 个人风格偏好；
- 没有收益证明的大规模重构；
- 项目明确排除的产品范围；
- 与当前实现无关的未来设想；
- 仅仅“可以写得更优雅”。

【报告结构】

最终报告必须包含：

1. 执行摘要：总体结论、P0/P1 数量、最重要问题、分支、HEAD、基线和工作区状态；
2. 范围与覆盖：深入检查、抽样检查、未检查目录以及选择依据；
3. 确认问题：按 P0、P1、P2 排序；
4. 候选问题裁决：记录 stale、duplicate、invalid、out-of-scope 和 needs-evidence，避免后续重复调查；
5. 架构评估：前端/backend、Tauri、Rust core、存储、进程、连接和路由、mock/生产隔离；
6. 成熟度评估：架构、正确性、错误处理、数据一致性、跨平台、测试、维护、日志、恢复能力和发布准备度；评分必须附证据，不能只给数字；
7. 测试与本机验证：命令、结果、失败分类、未运行项及原因；
8. 多模型记录：实际调用的 Agent/模型、分工、分歧、不可用模型以及主 Agent裁决；
9. 待验证风险和残余风险；
10. 建议顺序：立即修复、下一轮、可选优化、不建议处理；
11. 最终结论：Review verdict: BLOCK、OK WITH REQUIRED FIXES、OK WITH NOTES 或 OK；
12. 报告文档检查结果：pnpm check:docs 的结果。
```
